# S1: data pipeline (Day 1, 13:15–15:00)

**Goal:** a month's trip file landing in the data bucket ends up as rows in Redshift and in the `zone_hour_stats` mart, with no one pressing a button. A file whose schema has moved never gets copied, and a month with bad data never reaches the mart.

## Recall check (5 minutes, no agent)

1. Why can you read a Parquet file's schema without downloading the whole file?
2. In Redshift, what does a sort key change, and what does a distribution key change?
3. What makes a load safe to run twice? Give one way to make a monthly reload idempotent.
4. A sensor and a schedule both start runs. When would you use each?

## Given

- `contracts/trips.schema.yaml` (the landed files' Parquet schema), `contracts/marts.sql` (the mart's DDL), `contracts/platform.yaml` (warehouse names, Dagster storage, partitions, which checks must block). Frozen.
- `infra/modules/redshift`: a single `ra3.large` node with `LabRole` attached. Its admin password is write-only and stored nowhere; everything talks to Redshift through the Data API as a named database user.
- `pipelines/`: the Dagster project (pinned 1.13.25). Resources `RedshiftData` and `DataBucket`; the `trip_months` partitions; assets `taxi_zones`, `trip_files` (a landed file, seen through its footer), `stg_trips` and `zone_hour_stats`; `reference/patterns.py` (one asset, one blocking check, one sensor); tests with fake Redshift and S3.
- `deploy/compose.platform.yaml` and `.github/workflows/platform.yaml`: Dagster on the platform host, deployed like your app. `.github/workflows/status.yaml`: tells the grader what your pipeline has loaded.

## Build

1. **Warehouse:** wire `infra/modules/redshift` into `infra/live/warehouse.tf` with the outputs `contracts/platform.yaml` lists. Plan, review, apply (about 2 minutes).
2. **Platform runner and deploys:** `scripts/register-runner.sh platform`, then:
   `gh variable set LAB_PLATFORM --body on`, `gh variable set LAB_DATA_BUCKET --body <bucket from the instructor>` and
   `gh variable set LAB_ARTIFACT_BUCKET --body "$(terraform -chdir=infra/live output -raw artifact_bucket)"`.
   Push, and the platform workflow deploys Dagster. Open it with SSM port forwarding (command in `deploy/compose.platform.yaml`) at http://localhost:3000.
3. **Schema check** (`pipelines/src/labpipes/defs/schema_check.py`): `schema_contract` on `trip_files` compares the file's footer with `contracts/trips.schema.yaml` before anything is copied. The contract says it blocks.
4. **`raw_trips`** (`raw_trips.py`): COPY one month into `ingest.raw_trips` so that re-running the month never duplicates rows.
5. **Data-quality checks** (`quality.py`) on `stg_trips`: nulls, ranges, duplicates, row counts. Measure real months in Redshift before you pick thresholds.
6. **Sensor** (`sensor.py`): when a file appears or changes under `trips/`, add its month as a partition and start one run from `trip_files` through `zone_hour_stats`. Turn it on and watch 2024-01..04 arrive.

## Decision points (one record each in `decisions/`)

- **COPY vs Spectrum:** load each month, or query the files in place? Both work in Learner Lab.
- **Blocking vs warning:** which checks stop the run, and every threshold, with the data that supports it.
- **Dist and sort keys** for the trip tables.

## Done when

- `make check` passes locally and in CI, and the platform workflow is green.
- In Dagster, `trip_files`, `raw_trips` and `stg_trips` have 2024-01 to 2024-04, `zone_hour_stats` is materialized, and `schema_contract` is blocking.
- `select zone, pickup_hour, trip_count, median_duration_min from marts.zone_hour_stats where zone = 'JFK Airport' order by pickup_hour` returns 24 rows (Query Editor v2: connect with temporary credentials as database user `labadmin`).
- The status workflow has run (`gh run list --workflow status`): it's how the grader sees your pipeline.
- Your three new decision records exist.

## End of day (18:45)

Pause Redshift: `aws redshift pause-cluster --cluster-identifier lab`. A paused cluster bills storage only; a running one costs about $13 overnight. Resuming takes about 3 minutes (`resume-cluster`), and Dagster runs fail until it's back.
